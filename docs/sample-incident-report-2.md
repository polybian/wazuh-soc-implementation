# Tabletop Walkthrough — Custom Rule 100001 Fires on SSH Brute Force

> **Tabletop exercise — expected detections, not observed events.**
> The detection logic referenced below is implemented in
> `rules/local_rules.xml` and the stock Wazuh ruleset. The timeline is a
> walkthrough of what the rules **should** produce given the scenario —
> it was not generated by running the stack. The Wazuh manager and agents
> were not run in production for this writeup, so there are no dashboard
> screenshots or observed log excerpts here. Hostnames, IPs, and accounts
> are scenario fixtures.

## Scenario
- **Exercise ID:** TT-002
- **Scenario:** a second password-guessing run against the same Linux
  agent, this time exercising **custom rule 100001** — the
  frequency-correlation rule written specifically so a brute force
  surfaces as one severity-12 alert instead of a pile of severity-5
  failures the analyst must count by hand. Unlike TT-001, **no logon
  succeeds** in this scenario — it rehearses the "attack failed"
  branch of the playbook.
- **Fixture systems:** `soc-linux-01` (Wazuh agent, group `soc-linux`),
  source host `soc-attacker-01` (192.168.56.30), targeted accounts
  `testuser`, `admin`, `root`.
- **Objective:** validate the custom rule's logic on paper and rehearse
  triage when the outcome is "no compromise".

## Expected detections
Custom rule **100001** should fire on the 6th rule-5716 authentication
failure from the same source IP within 60 seconds. The rule is a
frequency-correlation child of the stock 5716 alert, written so the
brute force surfaces as **one severity-12 alert** instead of a pile of
severity-5 failures. MITRE mapping on the alert: T1110.001 (Brute
Force: Password Guessing). The dashboard filter for this scenario:
`rule.id: 100001 AND agent.name: soc-linux-01`.

## Triage (as the analyst would work it)
1. Open the 100001 alert in Threat Hunting; confirm source IP
   192.168.56.30, the targeted accounts, and that all failures came
   from the one source.
2. Pivot to the `soc-linux-01` timeline filtered by source IP,
   looking specifically for rule **5715** (authentication success) —
   **expect none**. Unlike TT-001, this brute force does not succeed,
   so no credential is treated as compromised.
3. Check for post-access behaviour anyway: no custom rule **100002**
   (sudo to root by a non-admin, parent 5402) and no FIM alerts
   (**100003**/100004, or stock 550/554) for the agent in the window —
   no sign of access, escalation, or persistence.
4. Check whether the same source touched other agents — no matching
   logon events would limit blast radius to one host, as designed.
5. Keep severity at High for the exercise: a severity-12 custom alert
   firing means the tuned threshold was crossed, even with the
   "attack failed" outcome.

## Scope / impact (scenario bounds)
- **Targeted (scenario):** SSH service on `soc-linux-01`; accounts
  `testuser`, `admin`, `root` guessed at. None compromised — no
  successful authentication from the source IP.
- **Not affected:** other agents, the Wazuh manager, any host outside
  the scenario network. No exfiltration, no persistence, no privilege
  escalation by design.

## Containment (playbook steps)
- Stop the guessing run at its source (`soc-attacker-01`) — in this
  exercise the "attacker" is the operator, so this is one command.
- Block 192.168.56.30 in the host firewall of `soc-linux-01`
  **manually**, as in TT-001. Stated explicitly: the active-response
  skeleton (`scripts/block-offending-ip.sh`) is **not** used — it
  dry-runs by design and is not connected to an `<active-response>`
  command in `ossec.conf`. Automating this step before a
  false-positive soak would be automating the risk, not the response.
- No account lockout: with no successful logon, locking `testuser`
  would only punish the environment's own test account.

## Eradication & recovery
- Nothing to eradicate — no access gained. Verify no new users, no
  changed `sshd_config`, no new authorized keys on `soc-linux-01`
  (FIM clean for the window; spot-check `~/.ssh/authorized_keys`
  for the targeted accounts).
- Remove the temporary host-firewall block after the exercise so the
  next run starts from the same baseline.
- Confirm the Wazuh agent remains Active and reporting, with the
  custom rules loaded (rule group `custom_rules` on the 100001 alert).

## Lessons rehearsed
- **The custom rule does its one job.** TT-001's lesson was
  "correlation beats severity"; 100001 is that lesson written as a
  rule. One severity-12 alert replaces the manual count-the-5716s
  triage, and the analyst's first question becomes "did anything
  succeed?" instead of "is this a burst?"
- **Tight thresholds are a test-environment luxury.** 6 failures / 60
  seconds fits a single-user test host and would be page-noise on any
  shared system. The rule header says so; if the environment grows a
  second human user, `frequency` is the first knob to revisit.
- **A failed attack is still a full rehearsal.** Because 100001 fires
  without a follow-on compromise, this run exercises the "attack
  failed" branch of the playbook — verify no success, no escalation,
  no persistence — which TT-001 never touches.
- **Active response stays manual for now, on purpose.** The AR
  skeleton exists, refuses bad input, and dry-runs — the remaining
  work before wiring it in is a false-positive soak of 100001 and a
  decision on block duration (`<timeout>` in the AR config), not
  more script features.
