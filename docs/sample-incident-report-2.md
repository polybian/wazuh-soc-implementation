## Detection
Custom rule **100001** fired on the 6th rule-5716 authentication
failure from the same source IP within 60 seconds. The rule is a
frequency-correlation child of the stock 5716 alert
(`frequency="6"`, `timeframe="60"`, `<same_srcip />`), written for
v2 of this implementation specifically so the brute force surfaces as **one
severity-12 alert** instead of a pile of severity-5 failures the
analyst has to count by hand. In this (simulated) run it fired at
15:02:38, while the guessing run was still in its first minute —
earlier in the attack than the INC-001 timeline, where the
analyst only picked the incident up after the fact from the stock
rules. MITRE mapping on the alert: T1110.001 (Brute Force: Password
Guessing). Dashboard filter used:
`rule.id: 100001 AND agent.name: soc-linux-01`.

## Triage
1. Opened rule 100001 in Threat Hunting; confirmed source IP
   192.168.56.30, the targeted accounts (`testuser`, `admin`, `root`),
   and that all failures came from the one source.
2. Pivoted to the `soc-linux-01` timeline filtered by source IP,
   looking specifically for rule **5715** (authentication success) —
   **none found**. Unlike INC-001, this brute force did not
   succeed, so no credential is treated as compromised.
3. Checked for post-access behaviour anyway: no custom rule
   **100002** (sudo to root by a non-admin) and no FIM alerts
   (**100003/100004**, or stock 550/554) for the agent in the window
   — no sign of access, escalation, or persistence.
4. Checked whether the same source touched `soc-win-01` — no
   matching logon events; blast radius is one test host, as designed.
5. Kept severity at High (simulated): a severity-12 custom alert
   firing means the tuned threshold was crossed, even though the
   outcome this time was "attack failed".

## Scope / Impact
- **Targeted (simulated):** SSH service on `soc-linux-01`; accounts
  `testuser`, `admin`, `root` were guessed at. None was compromised —
  no successful authentication from the source IP.
- **Not affected:** `soc-win-01`, the Wazuh manager stack, any host
  outside the test network. No data exfiltration indicators, no
  persistence, no privilege escalation observed.

## Containment
- Stopped the guessing run at its source (`soc-attacker-01`) — in
  this exercise the "attacker" is the operator, so this is one command.
- Blocked 192.168.56.30 in the host firewall of `soc-linux-01`
  **manually**, as in INC-001. Noted explicitly: the v2
  active-response skeleton (`scripts/block-offending-ip.sh`) was
  **not** used — it dry-runs by design and is not yet connected to
  an `<active-response>` command in `ossec.conf`. Automating this
  step before a false-positive soak would be automating the risk,
  not the response.
- No account lockout applied: with no successful logon, locking
  `testuser` would only have punished the environment's own test account.

## Eradication & Recovery
- Nothing to eradicate — no access was gained. Verified no new
  users, no changed `sshd_config`, no new authorized keys on
  `soc-linux-01` (FIM clean for the window, manual spot-check of
  `~/.ssh/authorized_keys` for the targeted accounts).
- Removed the temporary host-firewall block after the exercise so
  the next test run starts from the same baseline.
- Verified the Wazuh agent remained Active and reporting, with the
  custom rules loaded (rule group `custom_rules` visible on the
  100001 alert).

## Lessons Learned
- **The custom rule did its one job.** INC-001's first lesson
  was "correlation beats severity"; 100001 is that lesson written
  as a rule. One severity-12 alert at 15:02:38 replaced the manual
  count-the-5716s triage from the first exercise, and the analyst's
  first question became "did anything succeed?" instead of "is
  this a burst?"
- **Tight thresholds are a test-environment luxury.** 6 failures / 60 seconds is
  right for a single-user test host and would be page-noise on any
  shared system. The rule header says so; if this environment grows a
  second human user, `frequency` is the first knob to revisit.
- **A failed attack is still a full rehearsal.** Because 100001
  fired without a follow-on compromise, this run exercised the
  "attack failed" branch of the playbook — verify no success, no
  escalation, no persistence — which INC-001 never touched.
- **Active response stays manual for now, on purpose.** The AR
  skeleton exists, refuses bad input, and dry-runs — the remaining
  work before wiring it in is a false-positive soak of 100001 and
  a decision on block duration (`<timeout>` in the AR config), not
  more script features.
