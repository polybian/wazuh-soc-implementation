# Tabletop Walkthrough — SSH Brute Force with Successful Logon

> **Tabletop exercise — expected detections, not observed events.**
> The detection logic referenced below is implemented in
> `rules/local_rules.xml` and the stock Wazuh ruleset. The timeline is a
> walkthrough of what the rules **should** produce given the scenario —
> it was not generated by running the stack. The Wazuh manager and agents
> were not run in production for this writeup, so there are no dashboard
> screenshots or observed log excerpts here. Hostnames, IPs, and accounts
> are scenario fixtures.

## Scenario
- **Exercise ID:** TT-001
- **Scenario:** an attacker runs a password-guessing attack over SSH
  against a Linux agent, then logs in successfully with a guessed
  credential — the classic "brute force → valid account" sequence.
- **Fixture systems:** `soc-linux-01` (Wazuh agent, group `soc-linux`),
  source host `soc-attacker-01` (192.168.56.30), target account
  `testuser` (no sudo rights, exists only for the exercise).
- **Objective:** rehearse the analyst workflow — detection, correlation,
  triage, containment — against the ruleset as written.

## Walkthrough timeline (relative times)
| Offset | Expected event |
|---|---|
| T+0 | Password-guessing run starts from `soc-attacker-01` against SSH on `soc-linux-01`, target account `testuser` |
| T+0 – T+2 min | A burst of failed SSH authentications (stock rule 5716, "sshd: authentication failed") — we would expect on the order of a few dozen failures for a typical wordlist run |
| T+2 min | Stock rule **5710** ("sshd: brute force trying to get access to the system", severity 10, MITRE T1110) should fire once the failure threshold is crossed |
| T+3 min | The attacker logs in **successfully** with the correct password for `testuser` — simulating a compromised credential |
| T+3 min | Stock rule **5715** ("sshd: authentication success", severity 3) from 192.168.56.30 |
| T+4 min | Analyst picks up the 5710 alert in Threat Hunting; triage begins |
| T+6 min | Timeline pivot confirms the 5715 success from the **same source IP** as the brute-force burst |
| T+10 min | `testuser` locked on `soc-linux-01`; the SSH session from .30 terminated |
| T+15 min | Source IP 192.168.56.30 blocked at the host firewall |
| T+30 min | `testuser` password rotated; agent confirmed healthy; exercise closed |

## Expected detections
Rule 5710 should fire after the burst of 5716 authentication failures
crosses the brute-force threshold. On its own, rule 5715 (successful
logon, severity 3) is routine — what elevates this scenario is the
**sequence**: a severity-10 brute-force alert immediately followed by a
successful logon **from the same source IP**. Both alerts would appear in
the agent's event timeline, MITRE-mapped to T1110 (Credential Access)
and T1078 (Valid Accounts).

## Triage (as the analyst would work it)
1. Open the 5710 alert in Threat Hunting; confirm source IP
   192.168.56.30 and target account `testuser`.
2. Pivot to the `soc-linux-01` timeline filtered by source IP —
   look for a 5715 successful logon and any interactive session.
3. Check FIM events for `soc-linux-01` in the window after logon —
   any file-integrity alerts or new systemd units would indicate
   persistence; their absence bounds the scenario.
4. Check whether the same source touched other agents — no matching
   logon events would limit blast radius to one host.
5. Treat severity as High: a valid credential must be assumed
   compromised once a brute force succeeds.

## Scope / impact (scenario bounds)
- **Compromised (scenario):** the `testuser` account on `soc-linux-01`
  only. No sudo rights; exists solely for the exercise.
- **Not affected:** other agents, the Wazuh manager, any host outside
  the scenario network. No exfiltration indicators by design.

## Containment (playbook steps)
- Lock the `testuser` account (`usermod -L`) on `soc-linux-01`.
- Terminate the attacker's SSH session.
- Block 192.168.56.30 at the host firewall of `soc-linux-01`.

## Eradication & recovery
- Rotate the `testuser` password to a new randomly generated value.
- Review `sshd_config`: password auth is enabled **only** because the
  scenario requires it; key-only auth is the hardening follow-up for
  any non-test use.
- Confirm the Wazuh agent remains Active and reporting after cleanup.

## Lessons rehearsed
- **Correlation beats severity.** A severity-3 "success" alert is the
  most important event when it follows a brute-force burst. A composite
  rule (5710 → 5715 from the same IP within N minutes → severity 12)
  would surface this automatically; writing that custom rule is the
  natural next exercise.
- The default ruleset should catch the noisy attack immediately — a
  good baseline. A slow, distributed brute force would likely slip
  under the threshold; noted as a known detection gap.
