> VM against their own VM. No real systems, users, or data were involved.

## Detection
Rule 5710 fired after a burst of rule-5716 authentication failures
exceeded the brute-force threshold. On its own, rule 5715 (successful
logon, severity 3) is routine — what elevated this incident was the
**sequence**: a severity-10 brute-force alert immediately followed by a
successful logon **from the same source IP**. Both alerts were visible in
the dashboard within the agent's event timeline, MITRE-mapped to T1110
(Credential Access) and T1078 (Valid Accounts).

## Triage
1. Opened rule 5710 in Threat Hunting; confirmed source IP
   192.168.56.30 and target account `testuser`.
2. Pivoted to the `soc-linux-01` timeline, filtered by source IP —
   found the 5715 successful logon at 21:13 and one interactive session.
3. Checked FIM events for `soc-linux-01` in the window after logon —
   no file-integrity alerts; no new systemd units (Test 5 artifacts
   absent), so no persistence observed in this (simulated) scenario.
4. Checked whether the same source touched `soc-win-01` — no matching
   logon events; blast radius limited to one test host.
5. Escalated in the report (simulated severity: High) because a valid
   credential must be treated as compromised after a successful brute
   force.

## Scope / Impact
- **Compromised (simulated):** test-only account `testuser` on
  `soc-linux-01`. The account has no sudo rights and exists only for
  this exercise.
- **Not affected:** `soc-win-01`, the Wazuh manager stack, any host
  outside the test network. No data exfiltration indicators.

## Containment
- Locked the `testuser` account (`usermod -L`) on `soc-linux-01`.
- Killed the attacker's SSH session.
- Blocked 192.168.56.30 in the host firewall of `soc-linux-01`
  (internal rule; removed after the exercise).

## Eradication & Recovery
- Rotated the `testuser` password to a new randomly generated value.
- Reviewed `sshd_config`: confirmed password auth is enabled **only**
  because the test scenario requires it; key-only auth noted as the
  hardening follow-up for any non-test use.
- Verified the Wazuh agent remained Active and reporting after cleanup.

## Lessons Learned
- **Correlation beats severity.** A severity-3 "success" alert is the
  most important event in the incident when it follows a brute-force
  burst. A composite rule (5710 → 5715 from the same IP within N
  minutes → severity 12) would surface this automatically; writing that
  custom rule is the next exercise.
- The default ruleset detected the noisy attack immediately — good
  baseline. A slow, distributed brute force would likely slip under
  the threshold; note as a known detection gap.
- Enrollment password + agent groups made rebuilding the target VM
  trivial, which keeps the environment cheap to reset between exercises.
